# 09 — Compliance Posture (Florida)

Written 2026-07-15 after a source-code compliance audit; **re-audited against source 2026-07-16** after the email-list signup and tokenized unsubscribe shipped. This is an internal reference for how this app's data practices line up with Florida law and reasonable baseline practice — **not legal advice**; have a Florida-licensed attorney review before treating anything here as final, especially the public `/privacy` and `/terms` pages this doc supports.

**Confirmed by grep, not assumption:** `/order` and `/catering` are `tel:`/`mailto:` links, not forms. There is no contact form, no ordering form, no payment path.

**Third parties and what they get.** OpenAI (`api.openai.com`), xAI (`api.x.ai`), Google Gemini (`generativelanguage.googleapis.com`), plus Supabase/Netlify as infrastructure. All five AI call sites transmit **menu content only** — board photos, prompts, menu text. **No customer PII ever reaches any AI provider**; verified two ways: by inspecting each call site, and by confirming the subscribers/email-fax services are imported only by their own routes/pages and by no provider code path. **One deliberate exception to the broader "no third party" claim since 2026-07-16 (owner's ask):** `email_fax_requests` submissions are also forwarded server-side to **Netlify Forms** after the Supabase insert, so Netlify stores a copy in its Forms inbox and emails the owner a notification — disclosed on `/privacy` (the Netlify bullet + the fax/email section). Netlify already transits every request as the host; this makes it a *store* of that one form's PII as well. The `subscribers` mailing list is untouched — it still lands in Supabase only.

**Browser storage** — complete inventory: the `site_locale` cookie (functional, set *only* on an explicit EN/ES click, holds `"en"`/`"es"`, no identifier); Supabase auth cookies (staff only — `src/proxy.ts` matches only `/admin`, `/login`, and non-public `/api`, so public pages are genuinely session-free); and the PWA service worker's app-shell cache. **No localStorage, sessionStorage, or IndexedDB anywhere** (grep across `src/` returns zero).

**Analytics: definitively none.** Zero analytics/tracking/error-reporting packages in `package.json` (the runtime deps are Supabase, Next, React, and Zod). No `<Script>`, no `<iframe>`, no `dangerouslySetInnerHTML`, no gtag/GTM/pixel/Segment/PostHog/Sentry anywhere in `src/`. The only Facebook references are an outbound link and an SVG icon. `/privacy`'s "no analytics or advertising trackers of any kind" claim is accurate.

**Logging is clean.** All eight `console.*` calls in `src/` log Supabase query-error objects; none touch credentials, passwords, keys, or subscriber PII.

## Two real issues the 2026-07-16 re-audit found, both fixed

1. **The Gemini adapter put the API key in the URL** (`?key=…`), while the OpenAI and xAI adapters correctly use an `Authorization` header. URLs land in proxy/CDN/server access logs, so this contradicted both `crypto.ts`'s own "never in a way that could end up in request logs" rule **and** `/privacy`'s claim that provider credentials are "never exposed to a browser or written to a log" — i.e. it made a live public claim false. Fixed by switching to the `x-goog-api-key` header. (Gemini is currently unused by any live task — OpenAI serves all three — so this was latent, not actively leaking.)
2. **The subscribe endpoint was a membership oracle.** It returned `alreadySubscribed: true`, so anyone could POST an address to an unauthenticated, `Access-Control-Allow-Origin: *` endpoint and learn whether it was on the list. The tell was internal inconsistency: the *unsubscribe* route already refuses to be probed this way ("an unknown token gets the same answer whether it never existed or was deleted"), so two routes were answering the same threat differently. Fixed — the endpoint now returns an identical `{ok:true}` either way. The service still distinguishes the cases internally (it must, to un-suppress a returning subscriber); it just no longer tells the caller. "You're on the list" is true in both cases, so no honesty was traded for the fix.

Also removed in the same pass: an empty `src/app/api/dev/set-session/` directory (leftover scaffolding, no route file, no live endpoint).

## Why exposure is low today

The public marketing site collects essentially no visitor data *by default*: `src/proxy.ts`'s matcher excludes every marketing route from the session middleware, there are no analytics/ad-tracking dependencies anywhere in the codebase, and Catering/Order are plain `tel:`/`mailto:` links rather than forms that submit anything to a server.

**This section's original claim — that the app's only two `<form>`s were staff-only and authenticated — was invalidated on 2026-07-16 by the Subscribers feature (docs/03).** The homepage now has a public, unauthenticated form that accepts a visitor's **email and/or phone number** and stores it (`POST /api/public/{slug}/subscribe` → `subscribers`). That is a genuine change in posture, not a footnote: this app now collects customer personal information directly, where previously the only personal information it held was the owner's own login email. See "Subscribers, reconsidered" below — **this doc's low-exposure framing predates that feature and the sections below have been updated accordingly.**

**Update (2026-07-15):** an anonymous visit is no longer strictly zero-cookie — the language toggle (docs/06) writes a single `site_locale` cookie (`en`/`es`), but only when a visitor actively clicks it, never on page load. It carries no identifying data, isn't used for tracking or analytics, and is a functional/preference cookie of the kind generally exempt from consent-banner requirements under both FIPA and the CalOPPA-driven `/privacy` posture below — but it does mean the literal "zero cookies" statement is now "zero cookies unless the visitor opts into a language preference." Not treated as a posture change; noted here for accuracy.

## Applicable law

- **Florida Information Protection Act, Fla. Stat. §501.171 ("FIPA")** — applies. Any business that acquires or stores Florida residents' personal information is a "covered entity"; the owner's own Supabase Auth login email qualifies. Requires reasonable security measures, breach notification within 30 days for incidents affecting 500+ Florida residents (to those residents *and* the Florida Attorney General), and secure disposal of personal information no longer needed. **Materially expanded 2026-07-16 by Subscribers:** the `subscribers` table now holds customers' emails and phone numbers — real Florida residents' personal information, in volume, rather than one staff login. The 500+ resident breach-notification threshold was previously unreachable in practice and now scales with the mailing list. The "secure disposal of personal information no longer needed" duty also now has real content: as of 2026-07-16 the answer is a **written manual-disposal policy** — no automatic pruning (deliberate; see "Subscribers, reconsidered"), the owner deletes on request from `/admin/subscribers`, and `/privacy` discloses exactly that.
- **Florida Digital Bill of Rights, Fla. Stat. §501.701 et seq. ("FDBR")** — does **not** apply. Florida's comprehensive consumer-privacy law is scoped to entities with $1B+ global gross annual revenue meeting additional data-volume/ad-revenue tests — far beyond a single-location restaurant. **Re-check this if the business ever becomes a multi-location group or franchise** (see "Re-check triggers" below).
- **CalOPPA** (California, but nationally-reaching in practice) — any commercial website reachable by California residents that collects personal information should post a privacy policy. Addressed by `/privacy`.
- **FDUTPA, Fla. Stat. §501.201** — general unfair/deceptive-practices backstop. No violation found; the main implication is that `/privacy` and `/terms` must stay accurate as the app changes, since an inaccurate policy is itself a deceptive-practice risk.
- **ADA Title III / WCAG** — not a Florida statute, but Florida (11th Circuit) sees a high volume of website-accessibility demand letters against small businesses and restaurants specifically. *Gil v. Winn-Dixie* (11th Cir. 2021) narrowed what counts as a covered "place of public accommodation" online, but that's no defense against a demand letter arriving in the first place. A WCAG 2.1 AA pass is worth doing on that basis alone.
- **Florida mini-TCPA, Fla. Stat. §501.059** — **still not triggered, but this is now the closest live edge.** Nothing sends SMS today, and this statute is about *making* telephonic sales calls/texts, not about holding a number. But as of 2026-07-16 the homepage collects **phone numbers** into a marketing list — the "revisit if SMS marketing is ever added" condition this line was written against is now one feature away, not hypothetical. If SMS is ever built, §501.059's prior-express-*written*-consent standard is the thing to design for **before** sending, and the consent would need to be captured at signup time — the current form's copy does not attempt to obtain it, so today's collected numbers likely could not simply be texted later on the strength of this signup alone.
- **TCPA Junk Fax provisions / Junk Fax Prevention Act (47 U.S.C. §227(b)(1)(C)) — newly relevant 2026-07-16.** Sending fax *advertisements* requires the recipient's prior express invitation or permission (or an established business relationship), and the `/email-fax-list` form **is exactly that permission**: the person affirmatively asks for the daily-special menu by fax, names their number, and picks the days. Two practical consequences: (1) **the `email_fax_requests` row is the consent record** — keep it for as long as faxing to that recipient continues (the admin intro says so), since deleting it deletes the proof; (2) faxed ads still must carry an opt-out notice on the first page under FCC rules even when solicited — that lands on however the owner actually sends the faxes (a fax service's cover page, typically), not on this app, but it's worth knowing when sending starts. Nothing in the app sends faxes; this is all about the list the owner sends from manually.
- **CAN-SPAM (15 U.S.C. §7701 et seq.)** — **newly relevant as of 2026-07-16**; not previously listed because no marketing list existed. Applies to commercial email once the owner actually sends any. Its baseline duties (accurate headers/subject, a functioning opt-out honored within 10 business days, a physical postal address in the message) mostly land on whatever sending tool is used later — **but see the honesty gap in "Subscribers, reconsidered" below, which exists today, before a single email is sent.**
- **PCI-DSS, COPPA** — not applicable; no payment processing, no children-directed features.

## The OpenAI data flow, reconsidered

**Corrected 2026-07-16** — this section previously described the photo going to `gpt-image-1` (`generate-image-service.ts`) to *generate* a styled image. That is no longer the pipeline. Two OpenAI flows exist today, both staff-initiated:

1. **Daily Specials extraction** — the photo of the restaurant's own handwritten board goes to OpenAI `gpt-4o` (vision) to be *read into structured JSON* (`src/lib/menu/parse-special-menu-service.ts`); the published image is then drawn locally by a deterministic renderer, with no AI pixels involved. The photo still leaves the building; only what OpenAI *does* with it changed (reads it, rather than redraws it). The legacy `gpt-image-1` path still exists in the codebase but is not used by the live flow.
2. **Menu translation** — Main Menu and Daily Special *text* (dish names, descriptions) goes to OpenAI `gpt-4o-mini` for EN→ES translation (`translate_menu` task). This flow did not exist when this doc was written. It sends no photos and no customer data — only the restaurant's own menu copy.

Worth being precise about *whose* data this is: a customer never submits anything to either pipeline and never interacts with OpenAI in any way — they only ever see the finished image. The photographed subject is a board, not a person, in the normal case. So this isn't really a "customer personal information disclosed to a third party" situation the way a privacy policy usually means that phrase. **Note this reasoning does not extend to Subscribers** — that *is* customer-submitted personal information, though it goes to Supabase only and is never sent to OpenAI or any other third party.

It's disclosed in `/privacy` anyway, for three narrower reasons: (1) if a specials-board photo ever incidentally includes a person in frame, that person's image *would* be processed by OpenAI, and the policy already covers that case without needing an update; (2) completeness — a privacy policy listing subprocessors is a normal expectation even when a specific flow is low-risk; (3) it's honest, which matters more for FDUTPA-style accuracy than for any specific disclosure mandate. The disclosure is deliberately light-touch (one paragraph, no subprocessor-agreement detail) to match the actual risk level — this is not being treated as a high-severity finding.

## Subscribers, reconsidered (added 2026-07-16)

The homepage mailing-list form (docs/03) is the first feature in this app to collect personal information *from customers*. It's low-volume and low-sensitivity — an email and/or phone number, no name, no account, no payment data, stored in Supabase under the same RLS/access model as everything else and never sent to any third party (including OpenAI). But it moves this app from "holds one staff login email" to "holds a list of Florida residents' contact details," which is the specific fact several sections above were re-checked against.

**The honesty gap this section originally recorded is now closed (2026-07-16).** The form promised "no spam, unsubscribe any time" while no unsubscribe mechanism existed; the copy was briefly softened to match reality, then a **tokenized unsubscribe** was built before the list was ever mailed and the original wording restored — it's now true. How it works, and why it's shaped this way:

- **The link is a capability.** Each subscriber row carries a unique `unsubscribe_token` (32 random bytes, hex). Possession of the link proves the holder received the mail, so `/unsubscribe` needs no session — it goes through the service-role client scoped by the token, same pattern as the signup insert. Unknown tokens get a generic "no longer valid", so the list can't be probed.
- **Opt-out suppresses, it does not delete.** `unsubscribed_at` is set and the row stays. Deleting would lose the record that the person opted out, and a later manual add or CSV re-import could silently put them back on — the exact outcome an opt-out is supposed to prevent. Accordingly `createSubscriberByOwner` **refuses** to re-add a suppressed contact (they must opt back in themselves), while the public form **does** clear `unsubscribed_at` if they sign up again, because that submission *is* their opt-in. The owner can still hard-delete a row when they want the data gone (FIPA's disposal duty above), and `/privacy` tells visitors both of these things.
- **The export is the enforcement point.** Until sending exists, the CSV *is* the mailing surface, so it excludes suppressed rows and carries each recipient's own `unsubscribe_url` as a column to merge into whatever tool sends. A tokenized link that never reaches an inbox would accomplish nothing.
- **Confirm-then-act.** The emailed link opens a page; a POST from its button performs the opt-out. A GET never mutates, because corporate mail scanners and link prefetchers routinely fetch every URL in a message and would otherwise unsubscribe people who never clicked. Repeat clicks are idempotent.

This also front-runs **CAN-SPAM**'s opt-out duty: the mechanism a sender needs (a working per-recipient opt-out, honored promptly) already exists and is wired into the export, rather than being retrofitted under a deadline after the first send.

**RESOLVED (2026-07-16, owner's call): `subscribers` RLS is now owner-only** — migration `20260706000029_subscribers_owner_only.sql` replaced `subscribers_all_member` with a policy scoped to `role = 'owner'`. This is a **deliberate, recorded exception** to the project's "the role boundary lives in the middleware, not in RLS" pattern (CLAUDE.md), made because this is the one table where that pattern had the least margin: customer PII, where a single middleware mistake would otherwise have been the only thing between an employee account and every customer's contact details. It was strictly tightening — employees were already route-blocked, every session-scoped read/write of the table lives behind `/api/subscribers`, and the public subscribe/unsubscribe paths use the service-role client (bypasses RLS) so they're unaffected. If a future table seems to deserve the same, make it a conscious decision against this precedent, not a copy-paste in either direction.

Verified live with real signed-in JWTs rather than the service-role client (which would have bypassed the very policy under test): an employee who is a genuine linked member — proven by the same session still reading `menus` and `main_menu_sections` normally — now sees zero `subscribers` rows and is refused on insert with an explicit policy violation, while an owner session reads, adds, and deletes normally through the real `/admin/subscribers` UI. The control matters: an employee's empty result would look identical if they simply weren't a member, so "denied" is only meaningful alongside "but still authorized everywhere else." The restaurant has one real employee account today, so this is a live boundary, not a hypothetical one. (RLS denies SELECT by filtering to zero rows, not by erroring — the absence of an exception is not the absence of enforcement.)

Three of the four items previously recorded here as open were closed on 2026-07-16 (the RLS change above, rate limiting, and the phone-only opt-out gap — see below); what remains open, still by design and recorded rather than overlooked:
- **Retention is a written manual policy now, not a gap (owner's call, 2026-07-16):** "no automatic deletion; the owner deletes on request, and anyone can ask for full erasure" is the adopted, disclosed policy — `/privacy` states it plainly ("nothing is deleted automatically on a timer"). Chosen over auto-pruning because pruning suppressed rows would reintroduce the exact silently-re-subscribed-after-opting-out failure suppression exists to prevent, and pruning "stale" subscribed rows is meaningless while nothing has ever been sent (no engagement signal exists). Revisit if the list grows large, or when sending/SMS ships.
- **Rate limiting shipped (2026-07-16):** both public POST endpoints (subscribe ~10/hr, unsubscribe ~30/hr per client) go through `bump_rate_limit()` (migration `20260706000030`, `src/lib/rate-limit.ts`). Privacy-preserving by construction: the counter key is an HMAC-SHA256 of the client IP keyed with a server-only secret — the raw IP is never stored, the hash can't be reversed by enumerating address space without the secret, and rows are swept after a day. **Fails open** so a DB hiccup (or the code deploying before the migration) degrades to "no rate limiting," never a blocked signup or — worse — a blocked opt-out. Disclosed on `/privacy`. Residual, accepted: a distributed flood from many addresses still gets through per-IP limits; the worst case remains a bulk-deletable spammed list.
- **Phone-only opt-out delivery closed (2026-07-16):** a second CSV export (`GET /api/subscribers/export/phones`, "Export phones" in `/admin/subscribers`) lists every still-subscribed row with a phone number alongside its `unsubscribe_url`, so if the owner ever contacts someone by phone manually the link can actually reach them. The email export is unchanged and both exclude suppressed rows. **This is explicitly not an SMS-marketing surface** — see mini-TCPA above; the export's own UI copy says so.
- **Still open — no double opt-in / consent record**: a signup stores contact details and a `source`, but no timestamped record of *what the visitor was shown when they consented*. Fine for email today; would need to be designed for deliberately before any SMS use (see mini-TCPA above).

## The fax/email daily-special list (added 2026-07-16)

The `/email-fax-list` page hosts a native form (replicating the owner's Microsoft Form, by the owner's pivot — entries land in our own `email_fax_requests` table instead of Microsoft's tenant). Third-party involvement didn't go to zero, though: by the owner's follow-up ask, each saved submission is **also forwarded to Netlify Forms** so Netlify emails the owner a notification (inbox copy + email — the trade of Microsoft for Netlify swaps which vendor holds a copy, and is disclosed on `/privacy`). The forward runs server-side *after* the insert and is best-effort: a Netlify failure can lose a notification, never an entry, and never emails a submission that didn't save (honeypot/rate-limit/validation all run first). Two owner-side notes: erasing someone on request now means deleting their row **and** the Netlify Forms submission copy (Netlify's Forms UI has per-submission delete), and Netlify's own Akismet spam filter can silently divert a legitimate notification to its spam folder — the admin list is the source of truth, not the inbox. What else it changes and doesn't:

- **Second customer-PII surface.** Business/first name, fax and/or email, requested days, and a free-text notes field (the first free-text customer input on the site — visitors may type anything into it, including things we didn't ask for; it's shown only on the owner-only admin screen and never rendered publicly). Disclosed in its own `/privacy` section ("The daily special, by fax or email"), including removal-on-request.
- **Same defenses as the homepage signup:** honeypot, Zod validation, per-hashed-IP rate limiting (`email_fax` scope). No enumeration concern — the endpoint has no membership state to leak (every valid submission inserts; the response is always the same `{ok:true}`).
- **Owner-only RLS** (migration `..031`) — the second conscious use of the subscribers exception, applied because it's the same class of data. The exception's scope is now clearly "customer-PII tables", still not a new default.
- **No unsubscribe token, deliberately** — unlike the mailing list, nothing here is sent by the app, and the sends are individually addressed manual fax/emails by the owner. The removal path is "contact us / reply", stated on the page and on `/privacy`; the owner deletes the row. If app-driven sending is ever built, revisit (a tokenized opt-out link in the emails would then be the CAN-SPAM answer, same as the subscribers design).
- **Retention:** the written manual policy above applies — plus the Junk Fax consent-record point (Applicable law), which cuts the *other* way: these rows should be **kept** while sending continues, not pruned.

## Breach notification procedure

If a security incident is discovered that may have exposed personal information (staff login data, provider API keys, uploaded photos, **subscriber emails/phone numbers, fax/email daily-special request contacts**):

1. Rotate any potentially-exposed credentials immediately (Supabase service role key, AI provider keys, `CRON_SECRET`) via the Supabase dashboard / provider consoles.
2. Determine scope: how many Florida residents' personal information was involved, and what categories (FIPA's notice trigger is 500+ affected Florida residents).
3. If 500+ Florida residents are affected: notify each affected individual and the Florida Attorney General's office within **30 days** of discovery (FIPA allows a limited extension for law-enforcement investigation delays). If 1,000+ are affected, also notify nationwide consumer reporting agencies.
4. Document what happened, what was exposed, and what was done — both for the notice itself and for future reference.

Given this app's current single-tenant blast radius (one restaurant, one owner account), a realistic incident here is small-scale, but the 30-day clock starts at *discovery*, not at confirmation — err toward starting this process early.

## Data retention & disposal

**Corrected 2026-07-16 — the previous version of this section overstated two things.** Verified against source:

- **Nothing customer- or staff-identifying is deleted automatically — and as of 2026-07-16 that is the *written policy*, not an undocumented gap.** The owner chose "no automatic deletion; deletion on request" over auto-pruning (see "Subscribers, reconsidered" for the reasoning), and `/privacy` discloses it. Grepping every migration, `src/app/api/cron/`, and `netlify/functions/` turns up no scheduled deletion of PII; the per-minute cron promotes publish schedules and nulls a *pointer*, never a subscriber row. The `on delete cascade` chains from `restaurants` are real but never fire, because nothing deletes a restaurant. (One deliberate, narrow exception since 2026-07-16: `rate_limit_counters` rows — which hold only keyed hashes, no PII — self-sweep after a day inside `bump_rate_limit()`.) The earlier wording ("deleted together if a restaurant's account is closed … once cleanup runs") described a cleanup that does not exist and an account-closure flow that was never built.
- **Deletion is entirely manual, and there are exactly two paths:** the owner bulk-deleting subscribers at `/admin/subscribers`, and the owner removing a provider key in Settings. A customer **cannot** delete their own row — unsubscribing suppresses only (by design; see above). Anyone wanting true erasure has to ask, and the owner does it by hand.
- **Provider API keys are not in Supabase Vault** (an earlier claim here, and in docs/01, that never matched the code). They're encrypted app-side with AES-256-GCM in `src/lib/providers/crypto.ts` — `[12B IV][16B tag][ciphertext]`, base64, master key from `PROVIDER_KEY_ENCRYPTION_SECRET` — and stored as base64 text in `provider_credentials.encrypted_key`. Ciphertext never leaves the server (the `PUBLIC_COLUMNS` allowlist omits it; only last-4 is ever surfaced). Removing a key deletes the row rather than deactivating it. The security property is fine; the mechanism was misdescribed.
- **Where this leaves FIPA's "secure disposal" duty:** defensible, and now *documented* — single-tenant, owner-managed, small data set, deletion on request, with the practice stated on `/privacy` rather than left implicit (the 2026-07-16 gap was that it was undocumented, not that it was wrong). Revisit if the list grows large enough that "manual on request" stops being credible, and properly if multi-tenant self-serve signup ships (docs/07), which would introduce a real account-closure flow that must trigger cleanup automatically.

## Re-check triggers

Reassess this document (and FDBR applicability specifically) if any of the following happen:

- The business expands to multiple locations or joins a franchise/corporate group.
- Online ordering, SMS marketing, or any customer-facing form/account system is added — each is a new personal-information-collection surface that needs its own line in `/privacy`. **This trigger has already fired once and was missed:** the email-list signup (2026-07-16) shipped before `/privacy` was updated, leaving the page claiming "We don't add you to a mailing list" while a mailing list existed. It's since been corrected — but the lesson is that this list is only useful if it's actually consulted *while* building, not audited afterward. Treat "does this change what we collect, store, send, or set in a browser?" as part of shipping any feature.
- Analytics, advertising, or any third-party tracking script is ever added — at that point, and not before, a cookie-consent mechanism becomes relevant.
- A security incident occurs — follow the procedure above regardless of scale.
