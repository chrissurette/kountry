# MyMenuAgent

A mobile-first PWA, doubling as the restaurant's own public website, that lets a single owner photograph their handwritten daily specials board, generate an on-brand styled image of it via AI, review/approve it, and publish it to the live site instantly with no redeploy.

## Confirmed stack (do not re-litigate)

- **Next.js 15 (App Router), TypeScript, Tailwind** — PWA + API routes + the restaurant's public marketing site, deployed on **Netlify** (superseded Vercel on 2026-07-14, owner's explicit call — see "Architecture pivot" below)
- **Supabase** — Postgres (RLS on `restaurant_id`), Auth, Storage (private buckets), Vault (encrypted provider API keys)
- **satori + resvg** for template PNG exports; **Netlify Scheduled Functions** for scheduled publishing

## Non-negotiable design rules

1. **Nothing restaurant-specific is ever hardcoded** — all identity, branding, and menu defaults come from the `restaurants` profile row. The public site and the Daily Specials image pipeline resolve branding from the profile at render/generation time.
2. **Every table carries `restaurant_id`** — this is the multi-tenant seam. Adding a restaurant must mean adding a row, never changing code.
3. **Publishing is a pointer flip** — immutable `published_snapshots` + `restaurants.live_snapshot_id`. Never introduce a publish path that requires a build or deploy.
4. **Provider API keys never reach the client** — encrypted at rest, decrypted only inside server handlers, never logged or echoed (display last-4 only). All AI calls go through the provider abstraction (capability interfaces + adapters), never direct vendor SDK calls from feature code.
5. **All surfaces read the same public API** (`GET /api/public/{slug}/menu` for Daily Specials, `GET /api/public/{slug}/main-menu` for the permanent menu): the site's own `/menu` page and homepage today, any future consumer (e.g. social publishing) later.
6. **Prices are integer cents** (`price_cents`) with a free-text `price_note` escape hatch.

## Explicitly deferred (design for, do not build)

- **Social-media posting** — future `publish_targets` type; see extension notes in docs/07.
- **Multi-tenant onboarding/billing** — schema is already multi-tenant-ready; only UI/billing work remains later.

(2) **Soup is now `soups[]` with generic `tiers: [{label, price}]`** instead of one hardcoded `{cupPrice, bowlPrice}` — the model reads the board's own size words (Cup/Bowl, Small/Large, or one unlabeled price); the LABELS table's `cup`/`bowl` entries and the renderer's Cup/Bowl literals are gone. (3) **`featured` is a list** too. (4) **Strikethrough prompt rule** (crossed-out items dropped, or flagged in `uncertainItems` if ambiguous). (5) `hasMeaningfulContent` now counts `veggiePlate`/`additionalSections` so a veggie-only or additional-only board can publish. **Backward compat is the load-bearing detail:** all stored `special_data`/`special_data_es` predates this shape, so `dailySpecialMenuSchema` is now `z.preprocess(migrateLegacySpecialData, baseSpecialMenuSchema)` — the migration wraps a legacy single `featured` object into `[obj]`, converts legacy `soup:{name,cupPrice,bowlPrice}` into `soups:[{name,tiers:[Cup,Bowl]}]`, and defaults missing `additionalSections`/`dessertsLabel`. It's idempotent (current-shape data passes through) and runs on every read of stored data (Review page load, render, translate). **Do NOT bypass `dailySpecialMenuSchema` and hand-read `special_data` — you'd get un-migrated legacy shapes.** Live-verified: a legacy draft (old cup/bowl soup) migrates into the new tiers and renders identically; a fresh extraction of a standard board produces clean array-shaped data (the soup came back with the board's own "cup"/"bowl" labels, proving the generic path); and a crafted board with two featured items, a single-price "Gumbo" soup, and Breakfast/Kids `additionalSections` all render correctly (each new section's heading, note, and items present in the SVG). The Review UI grew array add/remove for featured/soups (+ per-soup tier rows) and a new "Other sections" accordion, all with EN/ES fields and index-aligned EN/ES array helpers (same pattern as entrees/combos). The public path is unaffected — it renders the immutable pre-rendered snapshot image, never the `DailySpecialMenu` schema — so none of this touched the live site.
- **Translation glued-conjunction artifact (2026-07-15):** the live Spanish special showed "Pollo yÑoquis" (for "Chicken & Dumplings") — two words run together. Debugged by char-code inspection of the stored `special_data_es` before touching any code: the missing space was **in the translation model's output itself** (`y` immediately followed by `Ñ` U+00D1, no invisible characters), not a renderer/whitespace bug — the deterministic SVG renderer drew exactly what it was given. gpt-4o-mini occasionally glues a single-letter Spanish conjunction (y/e/o/u) onto a following capitalized word, seemingly around accented capitals. Fixed three ways: (1) `src/lib/i18n/normalize-translation.ts`'s `fixConjunctionSpacing()` — a deliberately narrow regex (`/\b([yeou])([A-ZÁÉÍÓÚÑÜ])/` → `"$1 $2"`) applied to every translated string in BOTH pipelines (`translate-special-service.ts` on each unit before `applyTranslations`; `main-menu/translate-service.ts` on each unit's name/description). Narrow on purpose: single-letter conjunction + capital is near-certainly the artifact, while a broader lowercase→uppercase splitter would mangle legitimate mixed-case names like "McRib" (unit-tested against exactly that: fixes "yÑoquis"/"oTazón"/"eHuevos", idempotent on correct text, leaves McRib/all-caps alone). (2) A "never run words together" rule added to both translation prompts. (3) The live data corrected, re-rendered, republished, and verified in the live ES SVG ("Pollo y Ñoquis" present, artifact gone). A full scan of the live special's ES strings found this was the only affected one.
